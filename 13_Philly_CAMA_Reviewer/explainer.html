Rebuilding mass appraisal on open data

By Jason Fan and Team 3, MUSA 5090

Explainer Reviewer ↗ Repository ↗

Quick lookModel-predicted and assessed values for every Philadelphia parcel, side by side.

Skills demonstrated

Google Cloud Functions and Cloud Run deployment, BigQuery SQL transformation, Python cloud functions, dashboard chart implementation in JavaScript, CORS and public bucket configuration, linting across JavaScript, CSS, SQL, and Python, open data integration.

Every property tax bill starts with a number somebody had to estimate. A city cannot appraise half a million parcels individually each year, so it uses computer-assisted mass appraisal, a model that predicts market value from property characteristics and recent sales and then runs at scale.

The model decides how much a household owes, and it also decides how that burden is distributed. Mass appraisal has a documented tendency to over-assess low-value properties relative to high-value ones, which makes the effective tax rate regressive even where the nominal rate is flat.

Almost nobody outside an assessor's office can check any of this. The assessed value is published, but the model that produced it usually is not, and there is rarely a second opinion available to compare it against.

This project builds that second opinion. It is a cloud-native mass appraisal pipeline for Philadelphia running entirely on open city data, and it ends in a public dashboard where anyone can look up a parcel and see its current assessment, its history, and an independent model's estimate side by side.

What we are releasing

The release has three parts, a pipeline, a model, and a reviewer.

The pipeline runs on Google Cloud Platform. It extracts property data from OpenDataPhilly, transforms it into a warehouse schema, loads it into BigQuery, and produces the map tiles and chart configurations the dashboard consumes. There are ten discrete task deployments, each independently redeployable, orchestrated through Cloud Functions across Cloud Storage, BigQuery, and Cloud Run.

The model is a BigQuery ML linear regression that predicts sale price from five parcel attributes. It trains on sales recorded from 1 January 2024 onward, then scores every parcel in the dataset and rounds the result to the nearest hundred dollars.

The reviewer is a public dashboard. A user can search any property by address or OPA/BRT number and see its current and prior assessed values next to the model's prediction. The map renders every parcel as a choropleth of assessed value on a Leaflet basemap, served from the pipeline's own vector tiles rather than from a third-party service. Analytics panels chart the tax-year assessment distribution and the current model assessments citywide.

How we built it

The input data is deliberately narrow and entirely public. It covers OPA property assessments and the full assessment history from the Philadelphia Properties and Assessment History dataset, PWD stormwater billing parcels, which carry the parcel geometry, SEPTA stops, which supply the transit distance feature, real estate transfers, which give a sales history back to 1999, and building and zoning permits, which show when a property was renovated.

Storage is tiered into four buckets, and the part worth copying is the separation rather than the specific names. Raw data holds source files exactly as downloaded. Prepared data holds one file per dataset, normalised to the schema BigQuery external tables expect. Temp data is scratch with a short retention. Public holds only what the dashboard is allowed to read.

Keeping the public bucket as an explicit, separately governed tier means an accidental exposure requires a deliberate copy rather than a permissions mistake.

The pipeline stages are:

  1. Extract. Download source datasets to raw.
  2. Prepare. Transform to JSONL or Parquet in the prepared bucket.
  3. Load. Create BigQuery external tables over prepared data, then core tables.
  4. Model. Build the parcel table, train the regression on recent sales, and score every parcel.
  5. Tile. Generate property map tiles and a GeoJSON tile info layer.
  6. Chart. Generate assessment bin transformations and chart configurations.
  7. Publish. Push dashboard assets to the public bucket.

Each stage is a separate deployment with its own documentation, so a failed stage re-runs without touching the others.

How our estimates compare with others

The natural benchmark is the city's own assessed value, and the reviewer puts the two beside each other for any parcel a user looks up. The pipeline stops there. It computes no correlation, no mean difference, and no error metric of any kind, so this page cannot report how far the model's estimates sit from the city's across the tax base.

The comparison a reader most wants is a ratio study, the standard method in mass appraisal. It computes assessment-to-sale ratios against actual arms-length sales and summarises them as a median ratio, a coefficient of dispersion for uniformity, and a price-related differential for regressivity. A price-related differential above 1.03 is the conventional threshold for regressive assessment.

The transfer data needed to run one is already in the pipeline.

Limitations

No accuracy has been measured. The pipeline trains a model and scores every parcel with it, and there is no train and test split and no evaluation step anywhere between those two operations. Nothing in the repository states how close the predictions come to observed sale prices, so the estimates the reviewer displays are untested rather than tested and found adequate.

Five features is a small model. Floor area, zoning, age, census tract, and transit distance leave out bedroom and bathroom counts, lot size, exterior condition, and sale type. Without sale type the training set cannot separate an arms-length sale from a transfer between relatives, and both are learned from equally.

Training uses a narrow window. The training table keeps only rows with a sale date on or after 1 January 2024. The model learns from a recent slice of the market and then scores the whole city, including the large majority of parcels that have not sold in that window.

A second opinion is not ground truth. A model that disagrees with the city's assessment is not thereby correct, because both are estimates. The reviewer earns its keep by surfacing disagreement for a human to investigate rather than by settling it.

Sales data is thin where it matters most. Mass appraisal accuracy depends on arms-length sales in the neighbourhood, and the neighbourhoods with the fewest recent market-rate sales are often the ones where over-assessment is most consequential.

Parcel geometry comes from stormwater billing. The PWD parcel layer is maintained for a different purpose than assessment, and edge cases including condominiums and split parcels do not always align with OPA records. The parcel table is built as an inner join, so any OPA record without a matching stormwater parcel is absent from both the training data and the scored output.

What is next

An evaluation step comes first. Holding out a share of the 2024 sales and reporting median absolute percentage error would turn the predictions from untested numbers into a defensible second opinion, and it is a small amount of SQL against tables the pipeline already builds.

The ratio study is next, because it turns the reviewer from a lookup tool into an accountability tool. Publishing a coefficient of dispersion and a price-related differential by neighbourhood would say something about the assessment system that no individual parcel lookup can.

Beyond that, the pipeline is built for scheduled refresh but the public artifact is a snapshot. Wiring the workflow to a schedule and versioning the outputs would let a reader see how a parcel's assessment moved across cycles.
